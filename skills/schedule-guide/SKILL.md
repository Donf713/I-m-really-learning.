# 定时任务向导

把「每天获取 AI 新闻」这样的基本内容变成可执行、可确认的任务。先帮助用户明确想得到什么，再补齐调度信息。使用用户的语言。

## 保留上下文

在当前对话维护以下需求状态，不要求用户填表，也不主动把个人信息写入文件：

- 原始需求、目标和主题。
- 每轮新增信息、已选方向、排除方向和明确限制。
- 受众或用途、内容范围、信息来源、交付形式、篇幅与筛选标准。
- 首次执行时间、时区、后续重复方式与触发条件；按需记录检查间隔、冷却时间、开始日期和结束条件。
- 已知可用的数据与工具、仍待确认的信息。
- 当前阶段：探索方向 → 生成方案 → 等待确认 → 创建完成。

用户后续补充是对累计需求的更新。除非明确要求重来，不清空前几轮选择；冲突时以最新明确要求为准，必要时只澄清冲突处。

## 逐轮引导

1. 从最短输入推断可讨论的主题。若已足够明确，跳过方向探索，直接整理方案。
2. 尚不明确时，先用一句话说明「目前理解」，再提出一个最能缩小范围的问题。问题必须结合所有已知信息。
3. 为这个问题给出通常 3～5 个具体方向，每个方向用一句话解释会获得什么内容。选项应有明显区别，允许单选、多选、综合方向和自由填写；不要强迫用户只能选编号。
4. 用户自由填写第二条、第三条基本内容时，将新信息与第一条及全部历史合并，生成更贴合的新方向，而不是重复最初的菜单。用户选了方向但还过宽时，继续提供该方向内部的分支。
5. 每轮只问一个主要问题，避免一次询问所有参数。可用的交互工具必须允许用户自由输入，并服从当前工具对选项数量的限制；否则直接用简短编号列表提问。提问后等待回答，不替用户选中选项。
6. 用户说「都要」时保留综合方向，提出合理的内容比例或筛选方式；仅在范围会影响可执行性时继续细分。用户说「你决定」时，可提出默认方案，并清楚标记建议值。

方向已明确的判断：目标、范围和输出形式足以写出稳定的执行指令，且不存在会明显改变结果的内容歧义。用户不需要使用特定的「方向确认」口令。不要为了凑轮次继续提问；也不要设定固定轮数，尚不明确就继续缩小范围。

内容明确后进入时间与重复规则引导。复用对话已提供的参数和客户端时区，不重复询问已明确的内容；区分用户指定值与建议值。未明确的执行时间和重复条件必须提问，不直接带入默认值；用户授权「你决定」时才提出建议供最终确认。

## 时间与下一次执行条件

按需逐轮询问，每轮仍只问一个主要问题，允许选择或自由填写：

1. **执行时间**：「你希望第一次在什么时间执行？」可提供现在开始、明天某个时间、指定日期时间等选项。重复任务还需明确每次执行时刻或检查时间窗口。将「早上」「有空时」等表述细化到可调度时间；已知时区直接沿用，未知则询问。
2. **重复方式**：「第一次完成后，什么情况下才进行下一次？」可提供固定周期、满足条件时、固定周期检查且满足条件才执行、只执行一次。根据任务列出具体例子，如每天 9 点、每周一、有新新闻时、价格跌到指定值时。不要把用户带向固定周期而忽略条件触发。
3. **细化规则**：固定周期明确间隔和起算点（固定日历时间或上次完成后多久）；条件触发明确可检测条件、阈值或变化标准、检查频率。组合模式同时明确检查时间和实际执行条件。一次性任务明确不再重复。
4. **再次触发与停止**：条件持续满足时，按需询问是每次检查都执行、只在从不满足变为满足时执行，还是有新事件才执行；需要时补充去重依据、最短间隔或冷却时间。只有任务需要边界时才询问重复次数、结束日期或目标达成即停止。

严格区分「定时检查」「实际生成或执行」「向用户通知」。例如用户选择每小时检查、有新内容才生成简报时，没有新内容的检查不会产生新简报；如果用户要每小时都执行、只在有变化时通知，则明确说明执行仍按小时发生。

平台仅支持定时调度、没有事件监听时，解释可用的轮询检查方案与延迟，由用户确认后采用；不要承诺事件发生即实时执行。若跨次比较、去重或按完成时间起算需要平台不具备的持久状态或动态调度能力，说明限制，给出可执行替代并确认后再创建。

结束本阶段前，能用一句话清晰说明：首次何时执行、下一次何时或满足什么条件才执行、条件持续满足时是否重复、何时停止。内容与调度都明确后再展示最终方案。

## 生成可确认方案

用户所说的「生成需要的信息」默认包括完整任务方案和可直接执行的任务提示词。若明确要求先看实际样例，使用可用工具生成一次代表性结果；只有确实获取到数据才将其称为最新结果。需要查互联网时，使用当前可用的搜索技能或工具；不在探索方向的每一轮做无关搜索。

在一次可审阅的输出中给出：

- 简短任务名称和具体目标。
- 最终内容方向、范围、来源或获取方式、筛选和去重规则。
- 输出语言、格式、数量或篇幅；必要时附简短格式样例。
- 首次执行时间、当地时间与时区、后续重复方式和条件；按需说明检查频率、去重或冷却规则及结束条件。
- 完整的执行提示词，包含每次运行能独立理解的上下文，不依赖「按照上面的要求」。
- 数据不可用或没有新内容时的行为；监控类任务的通知条件。

参数按任务实际需要取舍。新闻任务应包含时间窗口、事件日期与发布日期的处理、原文链接和事实/传闻区分；监控任务应包含有意义的变化条件与终止条件。不要向普通用户展示 RRULE、内部工具字段或无助于决策的实现细节。

只承诺当前环境可获取的数据和可交付的结果。不要默认拥有私有账号访问权限、后台常驻能力或邮件/聊天发送权限。发送到外部服务需要相应授权和可用能力；不能执行的交付方式在方案中明确说明并给出可行替代。

最后用一个简短问题请用户确认这份具体方案并授权创建，例如：「按这份方案创建定时任务吗？也可以直接告诉我想修改的部分。」

用户明确说「不用创建」「仅生成提示词」时，交付方案后停止，不追问创建，也不调用创建工具。创建或安装本 skill 本身不代表授权创建任何真实定时任务。

## 确认后创建

只有用户确认了最终方案并授权创建，才执行创建动作。仅选择内容方向、说「继续」或确认某个局部参数，均不等于授权创建。若用户在确认时修改了影响任务行为的内容，更新方案；修改已明确且包含「按这个创建」等授权时可直接执行，否则再确认修改后的方案。

1. 发现当前 Agent 实际提供的定时任务创建、查询和更新能力，读取当前工具契约。支持原生调度的 Agent 使用其已授权能力；不要假定工具名或参数跨平台相同。Codex 环境优先使用 `automation_update`。
2. Codex 环境中，周期性跟进默认创建当前聊天的 heartbeat；只有用户明确要求每次新建任务或独立项目工作时才使用 cron。使用 cron 前通过 `list_projects` 获取项目，不能编造项目 ID。其他 Agent 按其原生调度语义选择用户确认的执行方式，不要求它实现 heartbeat。
3. 更新已有任务时先查找匹配的自动化配置，保留用户未要求修改的字段；确有重复风险时检查现有任务，避免再建一份。新建和修改均只能覆盖用户确认的范围。
4. 将最终提示词写成人类可读的完整指令。对监控类 heartbeat，除非用户明确要求周期性汇报，设置为状态不变或没有可操作变化时保持安静，仅在有意义变化、完成、失败或需要用户操作时通知。用户要求的每日新闻简报按日交付，不套用静默监控规则。
5. 用确认的首次时间、重复方式和时区构造工具所需的调度字段，将条件检查、再次触发和停止规则写入执行提示词或平台支持的配置，核对其对应的当地执行时间。确认平台确实支持该规则，不能把仅通知过滤当成执行条件。工具要求的字段若无法可靠推断，向用户补问，不伪造。
6. 工具成功后报告任务名称、实际频率/时间/时区、状态和已确认的主要内容。工具返回可用的管理入口时一并展示。只在返回确实支持时报告下一次执行时间。
7. 创建失败时明确报告未创建及可操作原因，并保留完整提示词和方案。对于超时或不确定响应，先核实任务是否已存在，避免盲目重复创建。工具不可用时交付可复制方案，说明当前不能实际创建。只有用户明确要求并授权其他调度方式时，才另行使用系统 cron、第三方服务等，不自动绕过原生工具限制。

## 跨 Agent 使用

核心引导流程不依赖特定平台。支持 SKILL.md 的 Agent 可加载本文件；其他 Agent 可将正文作为自定义指令。`agents/openai.yaml` 是 Codex 的可选界面元数据，其他平台可以忽略。交互工具不可用时，用普通对话完成逐轮选择和确认。缺少客户端时区时询问用户，不从文件路径或服务器时区推断。

## 累计收敛示例

用户：「每天看 AI 新闻。」

第一轮可提供工具产品、技术研究、商业动态、综合简报等方向，并说明各自内容。

用户：「还想知道哪些可以用于电商。」

第二轮基于「AI 新闻＋电商应用」提供商品图与视频、客服与销售、运营分析、电商综合等更具体方向。

用户：「选商品图与视频，重点是小团队能用的。」

现在整合为「面向电商小团队的 AI 商品图与视频动态」，整理适用场景、使用门槛、官方链接等内容规则，补齐或建议执行时间，展示完整方案。用户确认并授权创建后再调用自动化工具。
